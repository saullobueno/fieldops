# Relatório da Fase 40

## Implementado

- **Convite de usuário**: `POST /admin/users` (`admin:manage_users`) cria um usuário com `status = 'invited'` (sem senha) e devolve um link de convite (`/convite?token=...`). `GET /admin/users` lista usuários da organização com papéis; `GET /admin/roles` lista os papéis disponíveis para o formulário de convite. `POST /admin/users/:id/resend-invite` gera um novo link para um usuário ainda não ativado.
- **Aceitar convite**: `POST /auth/accept-invite` (público) verifica o token, define a senha, muda o status para `active` e já retorna uma sessão logada (mesmo cookie httpOnly da Fase 39).
- **Recuperar senha**: `POST /auth/forgot-password` (público) gera um link de redefinição para um usuário ativo; `POST /auth/reset-password` (público) verifica o token, define a nova senha e também retorna uma sessão logada.
- **Trocar senha autenticado**: `POST /auth/change-password` (`@RequirePermissions()` sem permissão específica — só exige sessão válida) verifica a senha atual e atualiza o hash.
- **Desativar/reativar usuário**: `POST /admin/users/:id/disable` e `POST /admin/users/:id/enable` (`admin:manage_users`), com transição de estado validada (só ativo→desativado e desativado→ativo).
- **Tokens de ação sem estado**: `createActionToken`/`parseActionToken` (`auth.guard.ts`) reaproveitam o esquema HMAC já usado pela sessão, com um `purpose` (`invite` | `password-reset`) e um `fingerprint` derivado de `computeCredentialFingerprint(userId, passwordHash atual)`. Como definir uma senha nova sempre muda o `password_hash`, isso invalida automaticamente qualquer token de convite/redefinição emitido antes — sem precisar de uma tabela de tokens nem de revogação explícita.
- **Frontend (`apps/web`)**: novas páginas `/usuarios` (listar, convidar, reenviar convite, desativar/reativar), `/convite`, `/esqueci-senha`, `/redefinir-senha` (públicas) e `/perfil` (trocar senha). Link "Esqueceu a senha?" adicionado ao `/login`. `AppShell` ganhou os itens de navegação "Usuários" e "Perfil".
- **Modo demo**: `UsersService`/`AuthService` usam um estado compartilhado em memória (`users/users.demo-store.ts`) para simular a tabela `users` quando não há Postgres — os 3 usuários semeados (`demoUsers`) mais qualquer usuário convidado durante a sessão do processo. Login em modo demo passou a autenticar contra esse estado mutável em vez de senha fixa, então convite → aceitar → trocar senha funciona de ponta a ponta mesmo sem banco.

## Bugs encontrados e corrigidos durante esta fase

- **Dois controllers com o mesmo prefixo `@Controller("admin")` no mesmo módulo quebram a injeção de dependência do NestJS.** Ao separar `UsersController` de `AdminController` (ambos em `AdminModule`, ambos `@Controller("admin")`), *todos* os métodos de *ambos* os controllers passaram a receber `this.service` como `undefined` em tempo de execução (sem erro no boot). Corrigido consolidando as rotas em um único `AdminController`. Isso não é um bug do meu código de negócio — é uma interação entre `tsx`/esbuild (que gera `design:paramtypes` de um jeito mais frágil que o `tsc` completo) e dois controllers competindo pelo mesmo path — mas vale registrar como armadilha a evitar no resto do projeto.
- **Mesmo depois de consolidar em um controller, a injeção de dois parâmetros de classe (`AdminService`, `UsersService`) no mesmo construtor ainda falhava.** Corrigido usando `@Inject(AdminService)`/`@Inject(UsersService)` explícitos em vez de depender da inferência implícita de metadados — o padrão que já era usado para tokens (`POSTGRES_POOL`) precisou ser estendido para classes também neste caso específico.
- **`UsersService.invite`/`resendInvite`/`setStatus` e `AuthService.acceptInvite`/`resetPassword`/`changePassword` não caíam no fallback demo quando o Postgres falhava tecnicamente numa escrita** (só as leituras — `list`/`listRoles` — já tratavam isso corretamente). Descoberto ao testar contra o Postgres real deste ambiente, que aceita `pool.query()` reaproveitando conexões antigas do pool mas rejeita `pool.connect()` para conexões novas (usado nas transações) — uma inconsistência real do Postgres local deste ambiente, não do código. Corrigido replicando o padrão já usado em `CustomersService` (`try` em volta de toda a tentativa Postgres, incluindo a obtenção da conexão, com fallback para a versão em memória em qualquer falha técnica — exceções de regra de negócio como `ConflictException`/`NotFoundException`/`BadRequestException` continuam propagando normalmente).
- **`AuthService.forgotPassword` engolia qualquer erro técnico do Postgres retornando `{}`** (sem gerar token), em vez de cair no fallback para `demoUsers` como os outros métodos passaram a fazer. Um usuário só existente no armazenamento demo (por ter sido convidado enquanto o Postgres estava tecnicamente indisponível) nunca conseguia gerar um link de redefinição. Corrigido com o mesmo padrão de fallback.

## Decisões

- Sem tabela de tokens de convite/redefinição: o esquema de fingerprint (derivado do `password_hash` atual) já invalida tokens antigos automaticamente ao definir uma senha nova, sem precisar de revogação explícita nem de um job de limpeza.
- Sem integração de envio de email: o link de convite/redefinição é devolvido diretamente na resposta da API (e mostrado na tela) em vez de "enviado" de verdade — decisão deliberada de manter o projeto 100% funcional sem custo/configuração extra de um provedor de email, consistente com a filosofia do projeto de só usar serviços gratuitos.
- Escopo do frontend restrito a `apps/web` (equipe de escritório/admin) — `apps/mobile-web` (técnicos) não ganhou telas de autoatendimento de senha nesta fase, já que hoje só administradores convidam/gerenciam usuários.

## Limitações

- Sem envio de email real — ver "Decisões". Isso expõe deliberadamente se um email existe na base ao usar "esqueci minha senha" (a resposta só inclui o link quando o usuário existe e está ativo), o que é aceitável para um projeto de portfólio/demo mas não seria para produção real com usuários externos.
- `apps/mobile-web` não tem `/perfil`, `/esqueci-senha` nem `/redefinir-senha` — um técnico convidado precisa que o admin gere o link de convite por ele; troca/recuperação de senha do técnico ainda dependem do fluxo web do admin.
