# Backlog de limitações por fase

Este documento consolida as limitações registradas nos relatórios de fase (`docs/phase-N-report.md` e `docs/roadmap-fase-NN-*-report.md`) que ainda estão em aberto. A estratégia combinada com o usuário é **não** reservar uma fase final só para fechar débito técnico — cada item aqui deve ser fechado oportunisticamente quando uma fase futura tocar na mesma área, e marcado como `Fechado` (com a fase/commit que resolveu) em vez de removido, para manter o histórico.

Formato de cada item: origem, descrição, fase mestre onde é mais provável de ser fechado, status.

## Aberto

7. **Busca de clientes limitada ao nome** — origem: Fase 8. Sem filtro por local, território ou contrato ativo. Fechamento: junto do item 6.
10. **Revogação antecipada de links assinados de anexos** — origem: Fase 7/15. Hoje o link só expira pelo tempo; não há revogação manual. Fechamento: junto do item 9, ou Fase 15 (Segurança/auditoria).
11. **Atualização otimista do checklist e edição/remoção de notas** — origem: Fase 9 (fatia de checklist/notas). A UI de ordens não faz atualização otimista, e notas não podem ser editadas/removidas. Fechamento: revisitar Fase 5/9 quando UX de ordens for refinada, ou Fase 16 (Performance/acessibilidade) para o aspecto de responsividade percebida.
15. **Sincronização sem Service Worker/background sync real** — origem: Fase 7. A sincronização automática depende da aba estar aberta (evento `online` + retry a cada 15s). Fechamento: quando houver uma fase dedicada a PWA/instalação mobile, hoje não prevista explicitamente no roadmap mestre.
16. **Sem UI de autoria de templates de checklist** — origem: Fase 9 (Formulários/Inspeções). A API de versionamento (`POST /checklist-templates/:id/versions`) existe e está testada, mas só é utilizável via API; não há tela para um administrador montar/editar campos de um template. Fechamento: revisitar Fase 9 quando houver demanda de uma tela administrativa dedicada.
18. **Validação de checklist só verifica presença, não formato** — origem: Fase 9. `form_fields.validation` pode carregar regras mais ricas (min/max, regex), mas `validateChecklistAnswers` hoje só checa se a resposta obrigatória está vazia. Fechamento: extensão natural de `validateChecklistAnswers` quando houver necessidade real de regras de formato.
19. **Filtros de equipe/território fixos na UI de relatórios** — origem: Fase 10 (Relatórios). Os seletores de equipe/território em `/relatorios` usam uma lista fixa com os dois times/territórios do seed demo, pois não existe endpoint de listagem de equipes/territórios. Fechamento: quando houver um módulo de administração de equipes/territórios.
21. **Pub/sub de tempo real em memória, por processo** — origem: Fase 11 (Tempo Real). `RealtimeService` usa um `EventEmitter` local; funciona com uma única instância da API, mas não escala para múltiplas instâncias sem um broker compartilhado (Redis já está disponível como infraestrutura do projeto, mas não conectado a isso). Fechamento: quando houver necessidade real de múltiplas instâncias da API.
22. **Localização do técnico não é persistida nem exibida** — origem: Fase 11. `POST /realtime/technician-location` só publica o evento; não grava em nenhuma tabela nem aparece no mapa do despacho/dashboard. Fechamento: Fase 6 (Despacho, aprofundamento do mapa) ou quando o mapa real for integrado (ver item 2/3).
23. **Eventos em tempo real só chegam na página Início** — origem: Fase 11. Despacho e ordens de serviço continuam dependendo de refetch manual/polling do TanStack Query, sem consumir o stream SSE. Fechamento: estender `useRealtimeStream` para `/despacho` e `/ordens` quando fizer sentido.
24. **`CalendarAdapter`/`MockCalendarAdapter` sem uso** — origem: Fase 3 (contrato criado), ainda aberto após a Fase 12. O contrato de bloqueios de agenda existe e é testado, mas nenhum fluxo da API o consome. Fechamento: quando houver necessidade real de sincronizar agenda externa (ex.: Google Calendar/Outlook) com a disponibilidade de técnicos.
25. **`HttpMapsAdapter` nunca exercitado contra rede real** — origem: Fase 12 (Integrações). A chamada HTTP ao OSRM só foi validada por injeção de dependência (adaptador falso) em teste automatizado, nunca contra um servidor real, seguindo a disciplina do projeto de não depender de rede em testes. Fechamento: validação manual pontual ao configurar `MAPS_PROVIDER_BASE_URL` em um ambiente com acesso à internet.

27. **Recomendações do copiloto só em memória, por processo** — origem: Fase 13 (Copiloto de IA). `CopilotService` guarda recomendações pendentes de aprovação num `Map` em memória; reiniciar a API descarta o que ainda não foi aprovado. Não há tabela dedicada no schema para isso (só `ai_conversations`/`ai_tool_calls`, usadas para conversa/evidência). Fechamento: adicionar uma tabela `ai_recommendations` quando o volume de uso justificar persistência entre reinícios.
28. **Datasets demo de dashboard e despacho não cross-referenciados** — origem: Fase 13, evidenciada ao testar o copiloto (mas pré-existente desde as Fases 4/6). O item de maior risco de SLA no `DashboardService` demo raramente corresponde a uma ordem não atribuída no `DispatchService` demo, então o encadeamento heurístico do copiloto quase sempre cai para "sem sugestão" em modo 100% demo. Com Postgres real o problema não existe (mesmas tabelas). Fechamento: alinhar os literais de dados demo entre os dois serviços, ou aceitar como uma limitação conhecida do modo demo.
29. **Caminho real do provedor de IA nunca exercitado contra a rede** — origem: Fase 13, atualizado na Fase 19 (migração Anthropic → Groq). Não há `GROQ_API_KEY` configurada neste ambiente; o loop de tool-use real e a saída estruturada em JSON foram validados só por tipos, testes com o cliente indefinido (caminho heurístico) e revisão de código. Fechamento: validação manual pontual ao configurar a chave em um ambiente com acesso à internet.

## Fechado

- **Console de despacho sem visualização de mapa** — origem: descoberto na Fase 22 ao revisar o código para integrar mapa real. Fechado na Fase 27: `/despacho` reaproveita `MapView` para plotar bases dos técnicos e ordens pendentes com coordenadas, usando os dados do próprio `DispatchBoard`.
- **Sem captura de assinatura via canvas, nem upload de anexos no mobile-web** — origem: Fase 23 (upload real de anexos). Fechado na Fase 26: o técnico pode abrir o detalhe da ordem no `apps/mobile-web`, enviar foto/documento e desenhar assinatura em canvas; a assinatura é enviada como PNG e vinculada via `POST /work-orders/:id/signature`. Upload e assinatura continuam online-first por dependerem de storage.
- **Checklist fora do fluxo offline do técnico** — origem: Fase 7. Fechado na Fase 26: o detalhe da ordem é cacheado em IndexedDB quando aberto, o checklist pode ser preenchido offline e sincroniza pela fila existente (`checklist_update`) ao voltar online.
- **CRUD de escrita para locais/contatos/contratos/ativos** — origem: Fase 8 (Clientes/Locais/Ativos) e Fase 18 (catálogo administrativo). Fechado na Fase 25: `CustomersService` e `CustomersController` ganharam criar/editar para locais, contatos, contratos e ativos; `/clientes` ganhou formulários inline por seção; modo demo e Postgres seguem o mesmo contrato. Limitações restantes: sem delete e sem telas administrativas separadas por catálogo.
- **Testes Playwright de comportamento offline do navegador** — origem: Fase 7 (Técnico/offline). Fechado na Fase 25: Playwright já está configurado com cenários para drag-and-drop do despacho e fluxo offline do técnico; `tsconfig.json` inclui `tests/**/*.ts`, e `pnpm e2e` passou com 2 testes.
- **Fotos/assinaturas sem upload real, e anexos sem storage em nuvem** — origem: Fase 9 (upload) e Fase 7/15 (streaming em nuvem). Fechado na Fase 23: `POST /work-orders/:id/attachments` (multipart) grava o arquivo via `StorageAdapter` (`packages/integrations`), local por padrão e Cloudflare R2 quando as variáveis `R2_*` estiverem configuradas; download também fecha o ciclo com URLs assinadas do R2 (`getDownloadUrl`) quando o arquivo não está no disco local. UI de upload adicionada em `/ordens`. Limitação restante: sem canvas de captura de assinatura nem upload no mobile-web — ver item 31.
- **Mapa sem provedor cartográfico real no dashboard** — origem: Fase 4 (Início). Fechado na Fase 22: o widget "Mapa ativo" do Início agora usa MapLibre GL real (`apps/web/src/lib/map-view.tsx`) plotando `latitude`/`longitude` reais de cada ordem (antes ignorados; a posição era só o índice do item no array). Tiles: estilo público `demotiles.maplibre.org` sem necessidade de chave, trocando automaticamente para MapTiler (free tier) quando `NEXT_PUBLIC_MAPTILER_KEY` for configurada. Ao revisar o código do despacho durante esta fatia, não foi encontrado nenhum mapa (nem fake) lá — a descrição anterior deste item estava imprecisa nesse ponto; ver item novo abaixo.
- **Login real / sessão persistente** — origem: Fase 2 (Auth/RBAC). Fechado na Fase 21: `POST /auth/login` com senha hasheada (bcryptjs), resolvendo permissões/equipes/territórios reais do Postgres (com fallback demo determinístico quando não há banco configurado). Telas `/login` em `apps/web` e `apps/mobile-web`, client HTTP autenticado substituindo os headers `x-fieldops-*` em todas as páginas. Limitação conhecida: sessão em `localStorage` (não cookie httpOnly) e token sem expiração/revogação — ver `docs/phase-21-report.md`.
- **Dependência de provedor de IA pago (Anthropic)** — origem: Fase 13. Fechado na Fase 19: `CopilotService` migrou de `@anthropic-ai/sdk` para `groq-sdk` (modelo `llama-3.3-70b-versatile`, free tier), mantendo o mesmo contrato de ferramentas somente leitura, loop de tool-use e saída estruturada validada por Zod. Decisão do projeto de usar apenas serviços gratuitos (Groq, Vercel, Render, Neon, Upstash).

- **Paginação "carregar mais" na UI de clientes/ordens** — origem: Fase 8/Fase 5. Fechado na Fase 16: `/clientes` e `/ordens` agora aumentam o limite consultado e exibem ação "Carregar mais" quando `items.length < total`.
- **Seletor de data no despacho** — origem: Fase 6. Fechado na Fase 16: `/despacho` agora permite escolher a data consultada e voltar para hoje pelo header.
- **Preview de pontuação/deslocamento de candidato durante o drag** — origem: Fase 6/Fase 12. Fechado na Fase 16: ao iniciar o drag de uma ordem não atribuída, `/despacho` consulta `GET /dispatch/candidates/:workOrderId` e exibe pontuação, conflito e deslocamento nas faixas dos técnicos.
- **Sem exportação de relatórios** — origem: Fase 10. Fechado na Fase 16: `/relatorios` exporta os dados carregados em CSV no cliente.
- **Filtro de auditoria por ator e período** — origem: fatias de auditoria. Fechado na Fase 15: endpoint de auditoria de ordens aceita `actorUserId`, `from` e `to`; a UI expõe os filtros.
- **Verificação visual não cobre CSS compilado** — origem: descoberto após a Fase 11. Fechado na Fase 17: o build foi validado procurando classes-chave no CSS compilado (`grid-cols-[236px_1fr]`, `max-lg:hidden`, `bg-[#B85C38]`) e a rota `/notificacoes` foi confirmada no manifesto/HTML gerado.
- **Estimativas de rota/deslocamento no despacho** — origem: Fase 6 (Despacho). Fechado na Fase 12 (Integrações): `HttpMapsAdapter` (OSRM real, com fallback para o mock) calcula o deslocamento entre a casa do técnico e o local da ordem; `DispatchService` usa isso na pontuação (`scoreAssignmentCandidate` ganhou o fator `travelMinutes`) e expõe `estimatedTravelMinutes` em cada candidato. Falta só conectar isso à UI de despacho (ver item 5, ainda aberto).
- **Sidebar/botões sem estilo (Tailwind não escaneava `packages/ui`)** — origem: introduzido quando o `AppShell` foi extraído para `packages/ui` (fatia da Fase 8). O Tailwind v4 (`@tailwindcss/postcss`, config só via CSS) não atravessa para pacotes irmãos do monorepo sem instrução explícita, então classes usadas só em `packages/ui` (`grid-cols-[236px_1fr]`, `max-lg:hidden`, `disabled:opacity-50` etc.) nunca eram geradas no CSS final de `apps/web`/`apps/mobile-web`, mesmo aparecendo certas no HTML. Corrigido em 2026-09-14 adicionando `@source "../../../../packages/ui/src";` em `apps/web/src/app/globals.css` e `apps/mobile-web/src/app/globals.css`. Confirmado no CSS recompilado e via `pnpm test`.
